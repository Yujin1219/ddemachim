# 장소 트렌드 수집 설계와 실험 이력

## 1. 이 문서가 설명하는 범위

이 파이프라인은 네이버 전체 블로그의 절대 언급량을 측정하지 않는다.
네이버 블로그 검색 API로 수집한 검색 결과 표본과, 그중 선별해 조회한
본문의 네이버 지도 데이터를 반복 관측한다. 따라서 결과의 의미는 다음과 같다.

> 설정된 지역·검색어로 수집한 네이버 검색 결과 표본에서 반복 관측된 장소

다음과 같은 표현은 사용하지 않는다.

- 네이버 전체 블로그에서 언급량이 몇 배 증가했다.
- 실제 검색량이 몇 건이다.
- 종로 전체 이용자의 관심이 몇 퍼센트 증가했다.

네이버 검색어 트렌드 API가 주는 값도 절대 검색량이 아니라 요청 그룹 안에서
정규화된 상대 관심도 지수다.

## 2. 최초 접근과 발견된 문제

### 2.1 제목·요약만으로 장소와 트렌드를 찾으려 한 단계

처음에는 지역명과 신상, 핫플, 웨이팅 같은 표현을 조합해 블로그 검색 API
응답의 제목과 요약에서 장소명을 찾으려 했다.

2026-08-12의 최초 검색 파일에는 다음 다섯 검색어가 남아 있다.

| 검색어 | 수집 결과 |
| --- | ---: |
| 안국 신상 카페 | 500 |
| 익선동 웨이팅 | 1,000 |
| 서촌 핫플 카페 | 800 |
| 북촌 오픈런 | 600 |
| 삼청동 요즘 뜨는 맛집 | 200 |

이 방식에는 세 가지 문제가 있었다.

1. 신상, 핫플, 웨이팅을 미리 정하면 발견할 트렌드의 종류를 기획 단계에서 제한한다.
2. 제목과 요약만으로는 문장 속 일반 명사와 실제 상호를 안정적으로 구분하기 어렵다.
3. 검색 결과에 노출됐다는 사실만으로는 글이 실제로 어느 장소를 다루는지 확정할 수 없다.

### 2.2 본문 네이버 지도 데이터를 이용한 장소 추출

장소명 추측 대신 블로그 본문의 v2_map 컴포넌트에 포함된 네이버 지도 장소를
구조화 데이터로 읽는 방식으로 바꿨다.

첫 본문 파일럿은 2026-06-13부터 2026-08-12까지의 안국 신상 카페 표본에서
50개 글을 선택했다.

| 항목 | 결과 |
| --- | ---: |
| 선택 글 | 50 |
| 본문 조회 성공 | 50 |
| 지도 포함 글 | 36 |
| 추출 장소 | 117 |
| 고유 장소 | 109 |
| 자동 확정 | 28 |
| 검토 필요 | 8 |
| 지도 없음 | 14 |

지도 포함 글 기준 자동 확정률은 77.8%였지만, 검색 지역과 무관한 부산·제주·수원
장소도 함께 추출됐다. 하나의 글에 여행 동선이나 여러 장소가 들어갈 수 있기
때문이다.

이 결과로 장소 존재 여부를 카카오 지도와 다시 일치시키는 방식보다, 네이버
지도 장소의 주소가 종로구인지 확인하는 것이 수집 목적에 더 맞다고 판단했다.
신규 장소나 팝업처럼 다른 지도 제공자에 아직 없는 장소를 탈락시키지 않기 위해서다.

## 3. 초기 트렌드 계산과 표본 부족

초기 파이프라인은 최근 7일과 이전 28일을 비교했다.

- 최근 고유 글 3개 이상
- 최근 고유 작성자 3명 이상
- 최근 검색 주제 존재
- 이전 28일 주간 평균 대비 증가

2026-08-12 중간 결과는 지도 검증을 통과한 12개 장소 중 관리자 검토 통과가
0개, 신규 후보 5개, 조건 미달 7개였다. 대부분 최근 글과 작성자가 0~1개여서
기간 비율을 계산해도 신뢰할 표본이 없었다.

이 단계에서 확인한 핵심은 절대 건수 또는 배수만으로 트렌드를 주장할 수 없다는
점이다. 블로그 검색 API 결과는 네이버 전체 글이 아니고, 검색 결과 순위와
중복 노출의 영향을 받는다.

## 4. 검색 범위와 본문 표본 확대

### 4.1 지역과 검색어 단순화

신상, 핫플, 포토존, 웨이팅 같은 선입견이 들어간 검색어를 제거했다.
현재 설정은 종로의 주요 지역 9개와 카페·맛집 두 문구를 조합한 18개다.

- 안국, 서촌, 익선동, 삼청동, 혜화, 부암동, 서순라길, 창신동, 동묘
- 각 지역별 카페, 맛집

지역 별칭도 함께 보관한다. 예를 들어 안국은 북촌, 서촌은 경복궁,
익선동은 종로3가, 혜화는 대학로를 포함한다.

### 4.2 9,000개 검색 결과와 500개 본문 표본의 차이

검색 API는 검색어마다 최대 500개를 100개씩 다섯 페이지로 요청한다.
이론상 18 × 500 = 9,000개이며 실제 2026-08-13과 2026-08-14 실행에서는
각각 8,981개의 검색 관측이 저장됐다.

9,000개를 모두 본문 조회하지 않는다. 검색 결과 전체는 후보군과 검색 순위,
중복 노출을 기록하는 데 사용한다. 본문은 비용과 차단 위험을 제한하기 위해
하루 500개만 query_balanced 방식으로 선택한다.

2026-08-14 표본은 14개 검색어에 28개, 4개 검색어에 27개를 배정해 정확히
500개를 구성했다. 이 수치는 500개를 검색어마다 읽었다는 의미가 아니다.

선별은 검색어 균형, 지역 최소 노출, 여러 검색어에 함께 나온 글, 검색 순위,
탐색 표본을 함께 고려한다. 같은 글이 여러 검색어에 나온 경우 URL 기준으로
한 번만 본문을 조회하고 각 검색 관측은 별도로 보존한다.

## 5. 현재 장소 추출과 통합 기준

1. 선별된 블로그 본문을 조회한다.
2. 본문의 v2_map 컴포넌트에서 placeId, 이름, 주소, 좌표, 전화번호를 읽는다.
3. 글에 여러 지도 장소가 있으면 검색 문맥과 위치를 기준으로 대표 장소를 선택한다.
4. 지도 주소가 종로구인지 확인한다. 종로구 밖 장소는 트렌드 후보에서 제외한다.
5. NAVER_MAP:{placeId}를 canonicalPlaceId로 사용해 같은 장소를 통합한다.
6. 같은 날짜·검색어·글 URL은 DB UPSERT 키로 사용해 재실행 중복을 막는다.

좌표가 없는 경우에도 NAVER_MAP 소스이고 종로구 주소가 명확한 블로그 트렌드
장소만 제한적으로 저장할 수 있다. 기존 장소와 같은 정규화 이름·종로구·도로명
주소가 단 하나 일치할 때만 자동 연결하며, 후보가 여러 개거나 주소가 다르면
검토 대상으로 남긴다.

## 7. 검색어 트렌드 API 적용 과정

### 7.1 일 단위 비교

처음에는 최근 7일과 이전 28일의 상대 관심도 평균을 비교했다. 그러나 장소가
많아질수록 일 단위 데이터와 유효 관측일 조건이 무거웠고, 사용자가 원하는
월간 변화 설명에도 맞지 않았다.

### 7.2 월 단위 재평가

기존 블로그 본문을 다시 읽지 않고 장소 목록만 네이버 API HUB 검색어 트렌드로
재평가하는 별도 명령을 추가했다.

- timeUnit: month
- 현재 월과 직전 완료 3개월 비교
- 2026-08-13 실행 기준 조회 기간: 2026-05-01 ~ 2026-08-13
- 이번 달은 13일까지의 누적값을 13일로 나눠 일평균으로 보정
- 장소 그룹은 최대 5개씩 API 요청

146개 장소를 30회 요청했으며 API 실패는 0개였다.

| 검색 관심 상태 | 장소 수 |
| --- | ---: |
| SURGING | 6 |
| NEWLY_EMERGING | 0 |
| STABLE | 124 |
| INSUFFICIENT_DATA | 16 |

월간 검색 관심과 블로그 근거를 다시 결합한 장소별 결과는 WATCH 2곳,
TRENDING 0곳, 근거 부족 144곳이었다.

- 와글와글베이크샵 익선: 글 8개, 작성자 8명, 월간 비율 9.4383, WATCH
- 리플린하우스: 글 2개, 작성자 2명, 월간 비율 2.2642, WATCH

과거 결과 파일은 장소별 재분류 후에도 상단 stats가 재평가 전 값을 유지해
WATCH 1개로 표시되는 불일치가 있었다. 현재 코드는 월간 재평가 후 WATCH,
TRENDING, INSUFFICIENT_EVIDENCE 요약도 다시 계산한다.

## 8. 현재 분류 기준

### 최소 근거

- 고유 글 2개 이상
- 고유 작성자 2명 이상
- 독립 intent category 1개 이상
- 수집일 1일 이상

### WATCH

최소 근거를 통과하고 아래 네 신호 중 두 개 이상을 만족한다.

- 고유 작성자 2명 이상
- 독립 intent category 2개 이상
- 수집일 2일 이상
- 검색 관심 상승

### TRENDING

최소 근거와 아래 조건을 모두 만족하고 광고 의심 글 비율이 50% 이하여야 한다.

- 고유 글 8개 이상
- 고유 작성자 3명 이상
- 독립 intent category 2개 이상
- 수집일 2일 이상
- 최근 관측 글 3개 이상
- 검색 관심 상승

현재 카페와 맛집은 모두 FOOD라는 하나의 독립 카테고리로 취급한다.
따라서 현재 18개 검색어만으로는 독립 intent category 2개 조건을 만족할 수
없어 TRENDING이 생성되지 않는다. 카페와 맛집을 억지로 서로 다른 독립 관심사로
계산하지 않기 위한 보수적 제한이며, TRENDING을 사용하려면 향후 별도의 독립
관심 범주를 추가하거나 기준 자체를 다시 합의해야 한다.

## 9. DB에 저장하는 데이터

blog_trend_observation에는 원문 HTML 없이 관측 근거만 저장한다.

- 장소 ID, 수집일, 검색어, 글 URL
- 작성자 URL과 표시명
- 게시일과 수집 시각
- 지역, 검색 의도, 검색 순위
- 본문 지도에서 관측한 장소명
- 광고 의심 여부와 감지 신호

place_trend_snapshot에는 날짜별 집계와 검색 관심 비교를 저장한다.

- WATCH, TRENDING, INSUFFICIENT_EVIDENCE 상태
- 고유 글·작성자·검색어·수집일
- 검색어별 표본 수와 상대 언급률
- 최근 관측 수와 평균 검색 순위
- 광고 의심 비율
- 검색 관심 데이터의 출처, 기간, 단위, 비율과 누락 월
- 데이터 의미를 설명하는 semantics

같은 날짜 재실행은 UPSERT하고, 날짜가 바뀌면 새 스냅샷을 만든다.
Spring 스케줄러의 기본 실행 시각은 Asia/Seoul 기준 매일 04:30이다.

## 10. 남은 한계와 운영 원칙

- 검색 API 결과는 전체 블로그 모집단이 아니라 검색 결과 표본이다.
- 검색 순위 알고리즘 변경이 관측 결과에 영향을 줄 수 있다.
- 본문 조회 실패와 지도 미삽입 글은 장소 관측에서 제외된다.
- 서로 다른 상호가 같은 이름을 쓰면 주소와 NAVER_MAP ID 확인이 필요하다.
- 광고 신호는 협찬 문구 기반 휴리스틱이며 광고 여부를 확정하지 않는다.
- 월간 검색 관심도는 그룹 내부 상대 지수라 장소 간 절대 크기 비교에 쓰지 않는다.
- 하루 또는 이틀 결과로 장기 유행을 확정하지 않는다.
- 결과 화면에는 근거가 충분한 상태만 노출하고, 원본 블로그 본문은 저장하지 않는다.
